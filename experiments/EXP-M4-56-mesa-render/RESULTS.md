# EXP-M4-56: semantically compiled vertex and fragment shaders

Target: T8132 M4, macOS 26.6.2 25G83. 2026-09-04.

Both shader mains compiled by Mesa now execute together through the standalone
GLES -> DRM-shim path and produce the expected 512x512 triangle. This is also
independently established in a Metal-hosted carrier for NIR-builder programs
and the exact GLSL-compiled shader bodies. Both original API main bodies are
disabled in the standalone archive. No shader-shape matching or captured
instructions enter the semantic compiler.

## Provenance

`probe.metal`, `literal.metal`, and `original-triangle.metal` are our source.
Only source-correlated operations in their `_agc.main` bodies were inspected
or mutated. Helper and launcher code was left opaque. Repeated explicit FMAs
in `probe.metal` reserve enough main space for independent generated programs;
these FMAs are not copied into Mesa. No proprietary Apple executable was
 disassembled or decompiled. The main/launcher packaging boundary alone is
not treated as evidence of ownership.

## Hardware contracts

- Vertex ID (`GET_SR 0xdd`) requires the slot-1 handoff in this vertex carrier.
  U2F consumption with each one-hot slot 0..6 returned the correct interpolated
  IDs only for slot 1. The ordinary path returned zero and collapsed all
  generated vertices. Compute's synchronous SR observations do not generalize
  to this graphics input. Mesa emits an allocated SR + routed identity-IOR
  pair, making the result ordinary before subsequent arithmetic.
- A vertex export reads an extended ALU publication, not an ordinary scalar
  literal/ALU destination. Replacing a known own-source 10-byte mode-3 literal
  with an ordinary 8-byte mode-2 literal made its export zero. A generalized
  FP32 ALU instruction with the two-byte extension and byte-4 publication bit
  restored the exact value. Clearing that bit was a negative control.
- The publication destination extension is different from ordinary ALU GPRs:
  the ordinary high-bank encoding failed. The compiler bounds published
  destinations to the low bank and allocates them normally. It currently
  publishes FP32 outputs with multiply-by-one, and keeps destinations live
  through completion. Reusing one destination for every export collapsed
  otherwise-valid geometry; distinct destinations worked.
- Ordinary iterator mode 0 reads both coefficient 0 (interpolated 1/W) and
  coefficients 1..4 (varying components over W). The old name of mode 4 as
  "W denominator" was misleading: coefficient 0 in that form returned zero.
  The compiler uses ordinary iteration, reciprocal, and multiply. Unequal W
  values 1, 2, 4 pass the perspective oracle.
- RT0 store format 0x4e consumes one packed RGBA8 u32. It does not consume two
  packed FP16 values. Literal 0xff4080bf yields RGBA bf,80,40,ff, including
  when emitted through independently relocated source registers. Mesa lowers
  clamp, scale by 255, round-to-even, conversion, and integer packing as NIR.

Earlier experiments based on replacing an assumed eight-byte native ALU span
were not decisive: those sources mixed extended/publication instruction forms.
The retained scripts include these failed hypotheses. The distinguishing
literal, routed-ID, and complete-program tests supersede them.

## Shader validation

`validate_mesa.py` computes its raster/color oracle on the CPU without using
native shader output. Four 64x64 cases each check all 4096 pixels:

| Case | Covered pixels | Maximum channel error |
|---|---:|---:|
| VS triangle, FS (R², G+1/8, B/2, 1) | 1152 | 0 |
| Same screen positions, W = 1,2,4 | 1152 | 1 |
| Smaller, shifted geometry | 288 | 0 |
| FS (1-R, G², 1/4+B/2, 1) | 1152 | 0 |

The first validation run's aggregate records are in `VALIDATION.json`; some
per-case files did not survive the first guest reset. Scripts and generated
bodies are retained for repetition. `validate_gles.py` additionally tests the
actual GLSL-compiled VS/FS extracted from `apple9-render-gles2.log`: 4096/4096
pixels pass, 1290 covered, maximum error one channel byte. Its full pixel log,
archive, and PNG are retained in `captures/t8132-25G83/`.

## Standalone Mesa / DRM-shim integration

The complete GLSL -> Gallium -> NIR -> Apple9 -> modern UAPI -> source-built
TA/3D path now completes, with both shader bodies generated by Mesa.
`apple9-render-clean.log` repeats two frames with the normal shim restored and
all experimental overrides removed. `apple9-render-mesa-owned.log` records the
same Mesa-owned mappings with passive attachment dumping enabled.

The standalone 512x512 attachment is validated by `validate_shim_attachment.py`.
Both frames have exactly 82,620 covered pixels, zero coverage/color mismatches,
and maximum color error one channel byte. Full attachment SHA-256:
`d487b7a84a08eb3287b1db13935e1ae5d2cf902a6e7a45055687d9fda7b9bc0f`.
The PNG and JSON reports are `captures/t8132-25G83/mesa-shim-triangle.*`.
The raw attachments are in `tmp/apple9-mesa-owned-graph/output-*-0.bin` relative
to the workspace. This is hardware output through Mesa, not a Metal-rendered
reference image or a software rasterizer.

Two independent integration defects were isolated:

1. The complete original native shader package also stalled through GLES.
   An own-source captured client graph passed the same current UAPI, including
   exact output oracles (`apple9-render-uapi-control.log`). The old shim had
   supplied template pages implicitly; Mesa's current fixed-USC view supplied
   only 2 MiB and omitted live fixed helpers/resources. Populating the full
   4 MiB view with its read-only executable and writable resource classes made
   the native control complete. Mesa now reserves and binds that view itself.
   The first render-context page is also explicitly authored, with a null
   trailing link; it is no longer inherited from a kernel template.
2. With that fixed, the generated VS retired but the generated FS stalled.
   Growing the old archive layout moved opaque helper blocks without a full
   relocation model. Appending both generated shader blocks after the fixed
   helper closure resolved the stall. All original helper offsets remain
   unchanged; only the known entry selectors are redirected. Both original
   API main bodies are overwritten with STOP, so a stale call cannot silently
   produce a native-shader triangle.

The temporary shim mapping override and native-package bypass were removed.
`shim-graph-diagnostics.patch` preserves the research instrumentation separately;
only its passive dump option was enabled for the validated Mesa-owned draw.
The m1n1 shim source was restored to its pre-experiment state, preserving the
user's existing edits.

Current limits: the opaque fixed color-load program still uses its captured
background (BGRA 0f0504ff), so this does not validate `glClearColor` semantics.
`glReadPixels` is outside this gate. The compiler supports procedural vertex-ID
geometry, one smooth VAR0 vector, FP32 arithmetic and one packed RGBA8 target;
vertex fetch, additional varying slots, arbitrary raster/attachment state and
graphics control flow remain unsupported. Unequal-W interpolation and changed
geometry/arithmetic additionally pass the independent Metal-carrier gates above.
No helper code was disassembled, decompiled, or reimplemented.

Host verification: all 184 compiler tests pass, including four new graphics
encoding/liveness/perspective/fail-closed tests. Mesa DRI and shim builds pass.

Shared-USC regression: the existing `gid` and `deep-float-dag` GLES compute
cases both pass on cold hardware (`tmp/apple9-render-compute-regression.log`).
